I Tried Making a Better OpenCode TUI.
It Got Out of Hand.

September 2026 ·Rust · OpenCode · TUI · AI ·~15 min read

I wanted a better TUI for OpenCode. That was the pitch. Not "a platform", not "an agent framework" — just: I don't like living in whatever client happens to be available, and Warp's terminal UI has interaction ideas worth stealing, so let me build my own little one around OpenCode.

It took five days. The idea is now two crates, roughly 19,000 lines of Rust, a memory system I did not plan, a decision layer that exists only in research documents, and a lot of notes explaining why each of those things happened.

This is the story of how that happened, including the parts where I was wrong.

Part 01The stupidly simple idea

The original scope was tiny, and I want to be honest about how tiny, because everything else in this article is downstream of not noticing the scope creep until it was expensive.

Original scope: a Warp-style block transcript, a multiline prompt, tabs for sessions, and a backend seam so the UI never had to know what server it was talking to. No memory. No decision-making layer. No "platform". Just a nicer way to drive OpenCode from a terminal.

Before writing any of it, I read Warp's source. Not to fork it — to understand how its TUI was put together. Two things came out of that week of homework.

First: the license is split. Warp's UI framework crates (warpui_core, warpui) are MIT; the rest of the repository, including the warp_tui crate I actually cared about, is AGPL-3.0-only. So the rule I wrote down for myself was simple: Warp is a reference, never a backend. I mapped the components, snapshotted seven presentation-only files into a frozen warp-tui/ folder for comparison, and left the Warp checkout itself untouched. It is still untouched. I check.

Why

Because "I looked at Warp's code" quietly becomes "I copied Warp's code" about two weeks later, and the week I wrote the rule down was the cheapest possible moment to write it.

Second: the parts of Warp's TUI that are actually good are the unglamorous ones. A block transcript where tool calls and shell output sit inline with the conversation. Gates — the little cards that block the transcript until you answer a permission request. A statusline that tells you what's happening. That list became my spec.

Part 02Building the TUI

The first version of OWT was a standalone Rust crate — binary owt — that ran against a scripted mock backend, because I wanted the interface to be real before the network was. The mock was deterministic: type something, get a scripted answer, trigger a fake tool call, answer a fake gate. Everything about the UI could be exercised with zero servers running.

From day one, the TUI never saw an OpenCode type. Views render snapshots; gestures call trait methods. This is the single decision I'd defend hardest, because it's the reason the mock and the real backend are interchangeable to the UI:

rust — tui/src/backend/mod.rs

pub trait Backend {
    fn session_summaries(&self) -> Vec<SessionSummary>;
    fn session_blocks(&self, id: &str) -> Vec<Block>;
    fn blocker(&self) -> Option<Blocker>;      // gate waiting on you?
    fn submit(&mut self, text: String);
    fn answer_question(&mut self, option: usize);
    // ... and later: compact, diff, revert, fork, model/agent switch
}

Some early things that only sound obvious in retrospect: the streaming pump polls a queue of StreamEvents on repaint, because spawned timers don't run under Warp's runtime — I found that out reading Warp's source, not by debugging my own bug. The scroll model got an explicit "pinned to bottom" flag after the classic usize::MAX hack quietly broke mid-word wrapping. And the theme went through a seam instead of inheriting Warp's builder, so the dark theme is mine and only approximately like theirs.

The part I'm happiest about isn't visual. It's scripts/pty_probe.py — a harness that drives the real binary under a pseudo-terminal and asserts on the exact character grid it painted. Eighteen checks: scrolling, wheel direction, pasted newlines, streaming, gates, cancel, tabs, help, exit, resizes. "It looks right in my terminal" stopped being evidence the day I wrote the first assertion.

What I didn't have, and wrote down as gaps instead of pretending otherwise: selection, vim motions, completion, real Markdown. markdown-lite is genuinely called that in the code.

Part 03Then came OpenCode

Here's where "simple TUI" stopped being simple. OpenCode needs a way to push live updates to a client instead of making the client ask "did anything happen?" constantly. That's what the server-sent-events stream is for, and that's what OpenCodeBackend is: blocking REST calls for commands (ureq, 15-second timeouts, no async runtime fighting the TUI loop) plus one subscriber thread for the event stream. The stream is live-only — if you miss events, the gap is real, so after a gap the adapter re-bases state from REST instead of trying to patch a hole in a stream it never received.

The boring middle is what made it feel like a tool instead of a wrapper:

  • Questions and permissions become gates you answer with digit keys.
  • History hydrates oldest-first, because the server's default newest-first order renders transcripts upside-down if you're careless — a bug I have now seen in other tools and will never unsee.
  • A dropped stream produces synthetic connection.lost / connection.restored signals, so stale busy state clears and you get one honest notice per gap instead of a spinner that never stops.
  • Every failure is an in-band error in the transcript. The session never dies silently.

And then the live probes started teaching me things the docs didn't say:

Problem

On OpenCode 2.0.8, the question tool never emits question.v2.asked. It materializes as a form.created event, and the answer goes back over a different route entirely. I found this by probing a live server with a throwaway session and then deleting the session, not by reading documentation — the documentation describes a world where the question tool announces itself politely, and that is not the world.

Other footguns, all found the same way:

  • The server 204-accepts model and agent ids that don't exist, and then takes your turn somewhere it can never be recovered from. So the client validates against server discovery and refuses to send garbage. A success status code that means nothing is worse than an error.
  • revert is two destructive operations wearing one name: staging it restores your files immediately, committing it deletes messages irreversibly. So it stages, shows you the actual affected files, and waits for a digit.
  • A forked session inherits history but not instruction entries or revert boundaries — close enough to correct that you'd only notice weeks later.

None of these are exciting. All of them are the difference between a TUI that demos well and one I'd still use next week.

Part 04Oh ma gwad

At this point I had: a TUI, a backend seam, a real OpenCode integration, gates, history, reconnects, and the advanced operations (compact, diff, revert, fork, model/agent switching). It worked. People — one person, me — could use it.

And then, with no prompting from history whatsoever, I had the following thought:

What if it remembered things?

Not "should agents have memory" as an abstract question. Specifically: this TUI starts a new OpenCode session every time, and every session starts amnesiac. It knows nothing about my preferences, my project, or the decision I made yesterday that it should have made again today. I wanted to fix that, and I want to be honest that this is the exact moment the project forked away from "weekend-sized".

Part 05The memory rabbit hole

My first instinct was the obvious one: a vector database. Then I spent three research phases trying to talk myself out of it, which is where most of the actual work in this project went.

Phase one was a survey: read how other systems do this — Mem0, Letta, Hindsight, OpenViking, a couple of others — and build a capability matrix. Almost all of them need an LLM for extraction, embeddings for retrieval, and a server for storage. The verdict from the comparison doc: exclude any design where the cloud is the default or the requirement. A personal TUI that needs an API key to remember your project is a worse TUI.

Phase two was the useful one: a minimality review of my own ideas, with the explicit goal of killing them. It killed the six-component design, it killed confidence scores, it killed SQLite and FTS5 "for now", and it landed on three components: a MemoryApi for explicit user commands, a MemoryStore (plain JSONL, one file per scope), and a Context Builder that assembles what gets injected.

Decision

The first version was deliberately boring: JSONL files, no database, no embeddings, no automatic anything. Not because those are bad ideas — because every one of them is a system I'd have to operate, debug, and explain, and none of them was needed to answer the original question.

What a memory actually is here — one line of JSONL:

json — one record, verbatim from the storage design

{"v":1,"id":"owt_1780000000000_1234_7","key":"lang","kind":"preference",
 "scope":"user","content":"Prefer Rust for new services.",
 "source":"user","status":"ACTIVE","pinned":true,
 "created_at":"2026-09-18T10:00:00Z","updated_at":"2026-09-18T10:00:00Z",
 "session_id":"ses_f4a63109effeiU7GgDsfKzJnSY","source_ref":"msg#3",
 "quote":"I'd rather write new services in Rust."}

Two kinds (fact, preference), two scopes (user, project), a status that only ever goes ACTIVE → SUPERSEDED (correction never silently overwrites), and — my favourite detail — no scores anywhere. No confidence, no importance, no novelty. If I can't justify a number, it doesn't get stored.

The unglamorous engineering is where the trust comes from:

  • Mutations rewrite the file through a temp file, fsync, and an atomic rename, so a crash mid-write can't leave a half-memory. Appends are for tombstones: a forgotten memory leaves a hash behind, so an extraction bug can't resurrect it next week.
  • flock plus an in-process mutex, because I run multiple sessions and they share the same store.
  • Secrets are refused outright — sk-, PEM blocks, ghp_, AWS keys, Slack tokens — with no state change. Not "warned about afterwards": refused, and the refusal itself is visible. Ambiguous shapes like label: value get stored with a warning.
  • Everything is 0600, directories are 0700, symlinks are refused.

Then the part that made it real: injection. The idea is one frozen owt.memory block, written into the session once at startup and never touched again — the agent doesn't get to rewrite its own instructions mid-conversation. The seam for this is OpenCode's session instruction entries, and I verified the edges against a live 2.0.8 server: writes return 204, and a 300 KB block gets rejected with a 413 and a very specific limit — 262,144 bytes. So the context builder is budgeted: 12,000 characters by default, assembled in a fixed tier order (project-pinned, user-pinned, project-recent, user-recent), with a hard ceiling on the encoded block.

And the commands are just commands: /memory remember, update, forget, pin, list, show. They get intercepted before the prompt becomes a network call, so a typo in a memory command never becomes a prompt to the model.

Phase 8 was the last push, and it was the one where I was most tempted to be reasonable-sounding and wrong. The research verdict for "memory intelligence" — extraction, retrieval, consolidation, the whole smart-sounding list — came back as: deterministic rules over your own messages, at session end, into a quarantine queue, and you confirm before anything is stored. No embeddings. No LLM. No daemon. I measured the alternative on paper first: LLM extraction meant 13 KB of prompts per pass, a cost line, and a model-config dependency, and my own rule was to measure the boring version's precision before paying for the clever one.

So the "intelligence" is: a few rules turn your sentences into typed suggestions, they're sorted by a lexical scorer that only decides the order things appear in (it never claims to know what's true), and then /memory suggest, confirm, discard. Quarantined files, atomic writes, thirty-day lazy expiry, secrets re-screened at confirm time. The agent proposes; I decide. That's the whole design philosophy of the memory system in one sentence.

Part 06Then I started researching Laya

Somewhere in there, the question I'm building for changed. It stopped being "can I make OpenCode look better?" and became "what would an agent system built around OpenCode look like if I controlled the surrounding architecture?" — which is a much bigger question, and I walked into it without noticing.

Zero Memory answers one question: what does the system know? Laya was the name I gave to a possible second layer that would answer a different one: what decision should be made? The idea is that a decision layer sits beside the model — not inside it, not replacing it — and owns the "which path do we take" question that a model otherwise guesses at.

Note

There is no Laya code in this repository. No prototype, no integration, no stub. It's an architectural direction that exists in the docs because separating "knowledge" from "decision" is the most useful thing I learned while researching memory — not because I built it. The UX research explicitly leaves it untouched: no decision-layer UI, no model-driven UI.

I mention it here because it's the clearest example of the pattern that got me in trouble in the first place: an idea that arrives as a legitimate question, gets a name, gets a research doc, and would very slowly have become a subsystem if I hadn't been paying attention. So I wrote the boundary down — Laya stays out of the memory system, by design, forever, until there's a reason and an authorization.

Part 07UX

The other thing that quietly became a project of its own was how the thing feels to use. This is what happens when you actually drive your own tool every day instead of demoing it.

Prompt history went in first, because retyping the same prompts was the most annoying thing in daily use — up and down recalls them, in-memory ring for now, disk later. Gates moved from digits 1–3 to digits 1–9, because sometimes the agent has more questions than a phone number can answer, and the footer started telling you what the digits do. Long shell and diff output collapses, because a transcript you have to scroll through to find the conversation is a transcript you've lost. A zero-state, so an empty session looks intentional. A working dot on the tab that's actually running a turn. Word-wise motion and kills in the prompt, because I miss them and they're twenty lines. Slash commands shared between both menus, so the same command doesn't live in two places with two behaviours.

And several things I decided not to do, which is most of the work: no side panels, no dashboards, no configurable nine-item statusline, no smart titles, no vim-mode editor port. The prompt box is not an editor. A deterministic UI that tells you exactly what state it's in beats a "smart" one that occasionally surprises you, and that's the whole UX principle of the project in one sentence. The UX research doc is seven documents long precisely because the answer to most questions was "no" and I wanted the reasons written down.

All of this — every UX item on that list — was view-layer work. No backend changes, no memory changes, no Warp changes. 245 tests passing, the pty harness at 19 checks.

Part 08Wait, what am I building?

Let me just list what's in the repository, because the list is the punchline:

  • A Warp-style TUI with tabs, transcript, gates, prompts, and menus.
  • An OpenCode integration: REST, SSE, sessions, history, reconnect, seven advanced operations, with a real backend boundary.
  • A memory engine: JSONL store, scopes, budgets, tombstones, secret refusal, injection.
  • Memory intelligence: rules, quarantine, suggest/confirm/discard.
  • Research into a decision layer that has no code.
  • A UX pass that is basically a second product.

Six things. I started with one. Nothing on that list is a stupid project, and that's exactly the problem — every one of them was justified, and the sum of six justified things is not "a weekend TUI" anymore. You don't notice this while each piece is going well. You notice it when you're mentally editing memory code at 1 a.m. and realize you haven't touched the UI in three weeks.

Part 09Splitting the project

So the project is now two folders that don't pretend to be one thing:

tui/ — the interface. Binary owt, the Backend trait, the OpenCode adapter. Usable today; this is the part I use.
memory/ — the zero_memory library. The store, the API, the rules. Finished enough to keep, separate enough to pick up later.

This wasn't a failure and it wasn't a rewrite. It's what the project had actually become: two things with different lifetimes and different reasons to change. The TUI ships on OpenCode's schedule; the memory system has opinions about extraction and budgets that don't change when OpenCode ships a new event shape. Coupling them meant every OpenCode upgrade was also a memory-system review, which is a coupling I chose and then didn't want.

The load-bearing wall never moved, by the way. The TUI still doesn't know what OpenCode is. That's the one architectural decision from week one that paid out over and over, including on the day I needed to stop and go look at the memory code.

Part 10Where I left it

TUIworking — usable today, the thing I actually run

Memoryseparated — zero_memory library, can be picked up later

Layaresearch — a direction, zero code, staying out of everything else

Phase 10planned — production hardening: migrations, crash recovery, version compatibility, the boring list

The repository is AGPL-3.0-only, eight commits, September 18 to 22. Tests went 144 → 195 → 239 → 245 across the phases; the pty harness went 18 → 19. Last touched the 22nd.

One more motive I should admit, because it explains a lot of the probing: much of the work was deliberately done against the free and cheap models OpenCode makes available — mimo-v2.5-free, muse-spark-1.3, whatever GET /api/model offered that week. I wanted to know first-hand how far modest models could be pushed through a real interface, not from papers. It's a builder's question, not a benchmark; there are no numbers in this article because I wasn't measuring. But the constraint made every design choice more honest: if a feature only works beautifully with a frontier model, this project doesn't really have it.

And the rule that ran the whole thing: if an idea couldn't survive contact with an implementation, it stayed a research document. That's what Laya is. That's what Phase 10 is. The pile of notes in research/ isn't a backlog of things I failed to finish; it's the honest record of what I was allowed to conclude before writing code.

I started this because I wanted a nicer TUI.

Now I have a nicer TUI, a memory system, a pile of research, a decision layer that doesn't exist yet, and two folders where there used to be one. The TUI works. The memory half is parked in a drawer I can open whenever I feel brave.

So — technically, mission accomplished. Mostly I just kept adding things, and the adding is the part I'd do again.
